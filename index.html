Le problème

Un git log que tout le monde a déjà vu…


a1b2c3d fix
e4f5g6h wip
i7j8k9l update
m0n1o2p ça marche enfin
q3r4s5t modifs suite review
u6v7w8x Merge branch 'dev' into dev
y9z0a1b correction bug

Qu'est-ce qui a changé ? Est-ce que ça casse quelque chose ? Quelle version publier ?

Demander à la salle : qui peut me dire ce qui a été livré dans cette version ? Personne. Et aucun outil non plus.

… et en code review

« Pourquoi tu n'utilises pas un Map ici ? »
« Ce nom de variable n'est pas terrible. »
« À revoir. »
  • C'est une question ou un ordre ?
  • Est-ce que ça bloque le merge ?
  • Est-ce que la personne est agacée ?
Même problème, autre support : le message ne porte pas son intention. Le lecteur doit la deviner, et il devine souvent le pire.

Le point commun

Un message sans structure oblige le lecteur à deviner.

Commits

Deviner la nature d'un changement

Changelog

Deviner l'impact d'une version

Comments

Deviner l'intention du relecteur

Une convention = un contrat de lecture partagé.

Partie 1

Conventional Commits

Donner du sens à l'historique

conventionalcommits.org

C'est quoi ?

  • Une spécification légère (v1.0.0) pour les messages de commit
  • Héritée de la convention du projet Angular
  • Lisible par un humain et analysable par une machine
  • Pensée pour s'aligner avec SemVer

Anatomie d'un commit


<type>[(scope)][!]: <description>

[corps optionnel]

[footer(s) optionnel(s)]

type

La nature du changement : feat, fix…

scope

La zone impactée : auth, api…

description

Résumé court, à l'impératif, sans point final

! / BREAKING CHANGE

Signale une rupture de compatibilité

Les types courants

TypeUsageImpact SemVer
featNouvelle fonctionnalitéMINOR
fixCorrection de bugPATCH
docsDocumentation uniquement—
styleFormatage, sans effet sur le code—
refactorNi feature ni fix—
perfAmélioration de performance— (souvent PATCH)
testAjout / correction de tests—
build / ciBuild, dépendances, pipelines—
chore / revertMaintenance / annulation—

Seuls feat et fix sont imposés par la spec — les autres sont des conventions courantes héritées d'Angular.

Breaking changes

Avec !


feat(api)!: supprimer l'endpoint /v1/users

Avec un footer


feat(api): passer la pagination en curseur

BREAKING CHANGE: les paramètres `page` et
`size` sont remplacés par `cursor` et `limit`.

Quel que soit le type → MAJOR

Le footer BREAKING CHANGE est l'endroit idéal pour documenter la migration : il finira tel quel dans le changelog.

Avant / après

Avant


fix
update
modifs suite review
correction bug login
ajout export

Après


fix(auth): gérer l'expiration du refresh token
feat(export): exporter les factures en CSV
refactor(invoice): extraire le calcul de TVA
docs(readme): documenter les variables d'env
test(auth): couvrir le cas du token révoqué

Un exemple complet


fix(payment): éviter le double débit lors d'un retry réseau

Le client relançait la requête de paiement après un timeout
alors que le PSP avait déjà accepté la transaction.
On envoie désormais une clé d'idempotence avec chaque requête.

Reviewed-by: Alice
  • La ligne 1 dit quoi
  • Le corps dit pourquoi (le code dit déjà comment)
  • Les footers relient au reste du monde (tickets, relecteurs, ruptures)

Pourquoi c'est utile ?

📖 Un historique lisible

On comprend un projet en lisant son git log. Onboarding facilité, archéologie du code simplifiée.

🔍 Un historique filtrable

git log --grep "^feat", retrouver tous les fixes d'un scope, préparer une démo…

🔢 Un versioning évident

Le prochain numéro de version se lit dans les types : plus de débat sur « c'est une mineure ou une majeure ? »

📰 Un changelog facilité

Chaque commit est déjà trié et décrit : rédiger les notes de version devient une simple relecture.

Pourquoi c'est utile ? (suite)

🧠 Ça force à réfléchir

Choisir un type oblige à se demander : « qu'est-ce que je fais vraiment ? ». Si ça ne rentre pas dans un seul type… c'est peut-être deux commits.

🧩 Des commits atomiques

Revues plus simples, git revert et git bisect plus fiables.

⚠️ Les ruptures sont visibles

Un ! se voit en revue, dans l'historique et dans le changelog. Fini les breaking changes cachés dans un « fix ».

🤝 Un langage commun

Devs, QA, PO, ops : tout le monde lit la même chose de la même façon.

Pièges à éviter

  • ❌ chore: stuff — le type ne remplace pas une bonne description
  • ❌ Tout mettre en chore pour « ne pas se tromper »
  • ❌ Un commit feat qui contient aussi 3 fixes et un refacto
  • ❌ Une liste de scopes infinie et incohérente → définissez-la en équipe

Partie 2

Conventional Changelog

Du commit au changelog

Pourquoi un changelog dans l'application ?

📣 Informer là où ça compte

Les utilisateurs découvrent les nouveautés dans l'outil qu'ils utilisent, pas dans un mail qu'ils ne liront pas.

🧭 Favoriser l'adoption

Une fonctionnalité non annoncée est une fonctionnalité inutilisée.

⚠️ Prévenir les changements

Un comportement qui change sans explication, c'est une surprise — et un ticket de support.

🙋 Réduire le support

« Est-ce que le bug X est corrigé ? » : la réponse est déjà dans l'application.

🤝 Créer la confiance

Montrer que le produit vit, s'améliore et que les retours sont écoutés.

🏆 Valoriser l'équipe

Le travail livré devient visible — pour les utilisateurs comme en interne.

Le changelog n'est pas un fichier technique pour les devs : c'est un canal de communication produit. Affiché dans l'application (page « Nouveautés », pop-up après mise à jour…), il touche les utilisateurs au bon moment.

Le lien : un commit ≈ une ligne de changelog

Dans le commitDans le changelog
featsection Ajouts
fixsection Corrections
perfsection Améliorations
! / BREAKING CHANGE:section ⚠ Ruptures, en tête, avec la migration
docs, test, ci, chore, style, refactoren général rien : invisible pour l'utilisateur
(scope)le domaine concerné
descriptionle texte de l'entrée (à reformuler si besoin)
footer Refs: #482le lien vers le ticket

Le tri est déjà fait au moment du commit.

De l'historique…


git log v1.5.0..HEAD --oneline
            

3f2a1c9 feat(api)!: passer la pagination en curseur
91be0d4 feat(export): exporter les factures en CSV
c7d8e2f fix(payment): éviter le double débit lors d'un retry réseau
a41e7b0 refactor(invoice): extraire le calcul de TVA
d0c33aa test(auth): couvrir le cas du token révoqué
5e9f120 chore(deps): mettre à jour les dépendances

En un coup d'œil : 1 rupture, 2 ajouts, 1 correction, et 3 commits sans intérêt pour l'utilisateur.

… filtré pour l'utilisateur…


git log v1.5.0..HEAD --oneline --grep "^feat" --grep "^fix" --grep "!:" --grep "BREAKING CHANGE"
  • v1.5.0..HEAD : uniquement ce qui a été fait depuis la dernière version
  • Chaque --grep ajoute un critère (il suffit qu'un seul corresponde) : les ajouts, les corrections et les ruptures (! dans le titre ou BREAKING CHANGE dans le footer)
  • refactor, test, chore… disparaissent : ils n'intéressent pas l'utilisateur

3f2a1c9 feat(api)!: passer la pagination en curseur
91be0d4 feat(export): exporter les factures en CSV
c7d8e2f fix(payment): éviter le double débit lors d'un retry réseau

👉 C'est le brouillon du changelog : une ligne = une entrée. Il reste à les ranger par section et à les reformuler pour les utilisateurs.

⚡ Une recherche git en local prend une seconde — bien plus rapide que de parcourir les commits, PR et work items dans Azure DevOps.

… au changelog


## [2.0.0] - 2026-09-28

### ⚠ Ruptures

- **api** : la pagination passe en curseur. Les paramètres `page` et `size`
  sont remplacés par `cursor` et `limit` (#475).

### Ajouts

- **export** : les factures peuvent être exportées en CSV (#471).

### Corrections

- **paiement** : un retry réseau ne provoque plus de double débit (#482).

Toujours écrit par un humain, pour des humains — mais en quelques minutes, sans enquête.

Remarquer que le rédacteur reformule : on passe de l'impératif technique à une phrase orientée utilisateur. Les commits donnent le tri, le contenu et les liens ; l'humain apporte le ton et le contexte.

Et le numéro de version ?

Les types de commits disent aussi quelle version annoncer.

Commits depuis v1.4.2Prochaine version
fix uniquementv1.4.3 — PATCH
au moins un featv1.5.0 — MINOR
au moins un ! / BREAKING CHANGEv2.0.0 — MAJOR

Plus de débat : il suffit de lire les types.

Pourquoi c'est utile ?

⏱️ Rédaction plus rapide

Le tri par type est déjà fait. On relit une liste structurée au lieu de mener une enquête.

🎯 Rien d'oublié

Chaque feat et chaque fix saute aux yeux : on sait ce qui doit apparaître.

⚠️ Ruptures impossibles à rater

Le ! et le footer BREAKING CHANGE signalent la rupture et fournissent la note de migration.

🔢 Version évidente

PATCH, MINOR ou MAJOR se lit directement dans les types.

🧾 Traçabilité

Scope et footer Refs relient chaque entrée à un domaine et à un ticket.

✍️ L'humain garde la main

On reformule, on regroupe, on contextualise pour les utilisateurs — sans perdre de temps à chercher.

Bonnes pratiques

  • Écrire la description du commit comme une future ligne de changelog
  • Documenter la migration dans le footer BREAKING CHANGE : elle sera recopiée telle quelle
  • Référencer le ticket (Refs: #123) pour garder le lien
  • Laisser chore, ci, test hors du changelog : il s'adresse aux utilisateurs
  • Reformuler du point de vue utilisateur : « un retry ne provoque plus de double débit »

Partie 3

Conventional Comments

Rendre l'intention visible

conventionalcomments.org

C'est quoi ?

  • Un format pour les commentaires de revue (PR, MR, docs, RFC…)
  • Chaque commentaire commence par un label qui annonce son intention
  • Optionnellement, des décorations qui précisent son poids

<label> [decorations]: <sujet>

[discussion]

Les labels

LabelIntention
praiseSouligner sincèrement quelque chose de bien
nitpickDétail de préférence, jamais bloquant par nature
suggestionProposer une amélioration concrète
issueSignaler un problème réel (idéalement avec une suggestion)
todoPetite action nécessaire mais triviale
questionJe ne sais pas, j'ai besoin de comprendre
thoughtUne idée qui émerge, pas une demande
choreTâche de process à faire avant d'accepter
noteInformation à connaître, rien à faire

Les décorations

(blocking)

Doit être résolu avant le merge.

(non-blocking)

N'empêche pas le merge. À traiter si on veut, maintenant ou plus tard.

(if-minor)

À faire seulement si le changement est trivial.

Vous pouvez définir les vôtres : (security), (ux), (test)… à condition que l'équipe s'accorde dessus.

🔎 Focus

L'intention

Le texte ne transmet pas le ton.
Le lecteur le reconstruit.

C'est LE cœur du talk. À l'oral, 90 % de l'intention passe par le ton, le visage, le contexte. À l'écrit, on perd tout ça. Le lecteur comble le vide, et les études sur la communication écrite montrent qu'on a tendance à surestimer notre capacité à faire passer un ton, et que le lecteur interprète plus négativement qu'on ne le voulait.

Un même message, trois lectures

« Pourquoi tu n'utilises pas un Map ici ? »

🤔 Curiosité

« Je ne connais pas la raison, explique-moi. »

💡 Suggestion

« Un Map serait sans doute mieux, qu'en penses-tu ? »

😤 Reproche

« C'est évident, tu aurais dû utiliser un Map. »

L'auteur du commentaire pensait à une de ces lectures.
L'auteur du code, fatigué un vendredi à 18h, en lira une autre.

Le label rend l'intention explicite

question: pourquoi un tableau plutôt qu'un Map ici ?
Je me demande s'il y a une contrainte d'ordre que je n'ai pas vue.
suggestion (non-blocking): on pourrait utiliser un Map ici.
Les lookups par id seraient en O(1) — mais ça reste marginal vu la taille de la liste.
issue (blocking): la recherche linéaire dans ce tableau est appelée pour chaque ligne.
Sur 50k lignes, on passe en O(n²) — un Map indexé par id réglerait le problème.

Même sujet. Trois intentions. Zéro ambiguïté.

Ce que l'intention explicite change

Pour l'auteur du code

Sait immédiatement quoi faire : répondre, corriger, Créer un PBI ou juste lire. Moins d'aller-retours.

Pour le relecteur

S'oblige à qualifier son retour : « est-ce vraiment bloquant ? » Souvent… non.

Pour la relation

Un nitpick annoncé ne ressemble plus à une attaque. On sépare la personne du code.

Pour l'équipe

Les juniors osent poser des question: sans passer pour des critiques ; les seniors ne passent plus pour des gardiens du temple.

Bloquant ou pas ? La question clé

Sans convention

Tous les commentaires ont le même poids apparent.

15 commentaires = « ma PR est mauvaise ».

L'auteur traite tout, ou arbitre au hasard.

Avec convention

1 issue (blocking), 2 suggestion, 10 nitpick, 2 praise.

= « une chose à corriger, le reste est du bonus ».

Priorisation immédiate, merge plus rapide.

Un volume de commentaires élevé est très souvent perçu comme une mauvaise note. Le label et la décoration permettent de trier la charge réelle.

praise : l'intention oubliée

praise: super idée d'avoir isolé la logique de retry dans un décorateur, ça rend les tests beaucoup plus lisibles.
  • La revue n'est pas qu'une chasse aux défauts : c'est aussi transmettre ce qui marche
  • Renforce les bonnes pratiques mieux qu'une règle écrite
  • Doit être sincère et précis — pas un « LGTM 👍 » de politesse

Avant / après

« Ce nom de variable n'est pas terrible. »
« Il manque des tests. »
« Tu es sûr de ça ? »
nitpick (non-blocking): data → pendingInvoices ? Ça aiderait à la lecture de la boucle.
todo (blocking): ajouter un test pour le cas où la liste est vide.
question: que se passe-t-il si le webhook arrive avant la réponse HTTP ? Je n'ai pas trouvé le cas géré.

Pourquoi c'est utile ? (récap)

🎯 Clarté

L'intention et le poids sont écrits, pas devinés.

⚡ Vitesse

Priorisation immédiate, moins d'aller-retours, merges plus rapides.

💬 Bienveillance

Moins de tensions, moins de sur-interprétation, plus de sécurité psychologique.

🧭 Discipline du relecteur

Qualifier un retour oblige à se demander s'il est vraiment utile.

📈 Exploitable

Parsable : stats de revue, filtres, bots, rappels sur les blocking.

🎓 Apprentissage

praise, thought, note transforment la revue en transmission de savoir.

Bonnes pratiques

  • Un commentaire = une intention. Deux sujets ? Deux commentaires.
  • Toujours expliquer le pourquoi dans la discussion
  • Un issue vient idéalement avec une suggestion
  • Préférer le « on » au « tu » : on parle du code, pas de la personne
  • Réserver (blocking) à ce qui compte vraiment
  • Côté auteur : lire le label avant de réagir au contenu
